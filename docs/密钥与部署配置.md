# 密钥与部署配置

这份文档说明**密钥怎么配、配在哪、配错了怎么查**。云同步的可用性完全取决于这里的配置。

---

## 1. 密钥层级

```
DEK  ── 32 字节随机数，加密全部账号数据（AES-256-CBC + HMAC-SHA256）
 │
 ├─ 被服务端 KEK 包裹   → header = { kdf:'server', wrappedDek }   零配置，默认
 │    KEK = HMAC-SHA256(VAULT_SECRET, openid)
 │
 └─ 被口令 KEK 包裹     → header = { salt, iter, wrappedDek }     手动开启，端到端
      KEK = PBKDF2(用户口令, salt, 100000)
```

`header` 在云端**只有一份**，后写入的覆盖先写入的。两种模式可在设置里**互相切换**：

| 动作 | header 变成 | 换机时需要 |
|---|---|---|
| 默认（首次同步） | `kdf:'server'` | 什么都不用输 |
| 设置里「启用口令」 | 口令包裹 | 输入口令 |
| 口令模式下点「切回零配置恢复」 | `kdf:'server'` | 什么都不用输 |

切换实现：先清本地 `header` 再 `push`——`push` 发现 `header` 为空，会自动向
`/api/wrap-key` 取 KEK 重新包裹。若切换失败（接口 503 / 网络断），会还原原 `header`，
不会让你卡在「既不能用口令、也不能自动恢复」的中间状态。

## 2. 必做：配置 `VAULT_SECRET`

### 2.1 生成

```powershell
# PowerShell
$b = New-Object byte[] 16
[System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b)
"saigou-" + (($b | ForEach-Object { $_.ToString('x2') }) -join '')
```

```bash
# macOS / Linux
echo "saigou-$(openssl rand -hex 16)"
```

输出示例（**不要直接用这串，自己生成**）：

```
saigou-e37ae448dfbdcee2d01a17fbc6b940bc
```

### 2.2 写入云托管

```
腾讯云 CloudBase 控制台
→ 云托管 → 服务 → 选中你的服务
→ 服务设置 → 环境变量 → 新增

   名称：VAULT_SECRET
   值：  saigou-e37ae448dfbdcee2d01a17fbc6b940bc

→ 保存 → 重新部署
```

### 2.3 强度要求

| 项 | 要求 |
|---|---|
| 长度 | **≥ 32 位**（服务端对 < 16 位打印告警） |
| 字符 | 随机十六进制或等价熵，**不要用 `saigou`、`123456` 这类词** |
| 唯一性 | 只用于本项目，不要复用其他系统的密钥 |
| **不能是公开信息** | 用户名、昵称、GitHub ID、手机号、生日一律不行——它们本身就是公开的 |

原因：`KEK` 的安全性**完全等于**这个值的熵。数据库泄露时攻击者拿到 `openid` + 密文 + 包裹后的 DEK，
如果 `VAULT_SECRET` 是字典词，用词表几秒就能还原 KEK，整套加密形同虚设。

**最容易被忽略的一种错**：用自己看得懂的名字，比如 `SaiGou_14H`、`saigou`。
它们就写在仓库地址、README、社交账号里——攻击者不需要爆破，第一次尝试就命中。
要兼顾记忆性，用「可识别前缀 + 随机后缀」：

```powershell
"SaiGou_14H-" + (($b | ForEach-Object { $_.ToString('x2') }) -join '')
# → SaiGou_14H-be57bcc04d707086e26f16512781d773   （43 位，可识别且不可猜）
```

### 2.4 绝对不能改

改了就等于**换了钥匙**：

```
旧 KEK 包裹的 wrappedDek → 新 KEK 解不开 → 拿不到 DEK → 历史密文永久无法解出
```

更换前必须先做迁移：本机解密出数据 → 换 `VAULT_SECRET` → 清 `header` → 重新上传。
没有这个流程就不要动它。

### 2.5 必须异地备份

它是**你数据可恢复性的唯一凭据**，重要性等同数据本身。

| 存放位置 | 评价 |
|---|---|
| 密码管理器（Bitwarden / 1Password / Edge 内置） | ✅ 推荐 |
| 纸质抄写 + 保险箱 | ✅ 最抗黑客 |
| 加密压缩包 + U 盘 | ✅ 可行 |
| 微信收藏 / 备忘录 / 聊天记录 | ❌ 明文、随账号同步、易泄露 |
| 项目仓库 / 代码注释 / 配置文件 | ❌ 等于公开 |

## 3. 数据库表

服务启动时自动创建，无需手工执行 DDL：

| 表 | 用途 | 关键字段 |
|---|---|---|
| `vault` | 当前密文 | `openid`(PK)、`data`、`rev`、`updated_at` |
| `vault_history` | 版本历史，保留 20 版 | `id`、`openid`、`data`、`created_at` |
| `migrate_token` | 换机一次性令牌 | `token`(PK)、`source_openid`、`expires_at`、`used` |
| `profile` | 身份资料（已不再使用） | `openid`(PK)、`nickname`、`avatar` |

验证（在云开发数据库控制台执行）：

```sql
SHOW TABLES;
DESCRIBE vault;
SELECT COUNT(*) FROM vault_history;
```

## 4. 验证清单

部署后按顺序跑，`BASE` 换成你的服务域名：

```powershell
$BASE = "https://express-w3rv-350067-13-1310828421.sh.run.tcloudbase.com"

# 1) 服务活着
curl.exe -s "$BASE/api/health"
# → {"code":0,"ok":true,"ts":...}

# 2) 密钥接口就绪（关键）
curl.exe -s "$BASE/api/wrap-key" -H "X-WX-OPENID: test123"
# → {"code":0,"kek":"<64位hex>"}        正常
# → {"code":503,...}                     VAULT_SECRET 没配 / 没重新部署

# 3) 版本历史接口
curl.exe -s "$BASE/api/vault/history" -H "X-WX-OPENID: test123"
# → {"code":0,"versions":[]}             新账号为空是正常的

# 4) 鉴权生效
curl.exe -s -o NUL -w "%{http_code}" "$BASE/api/vault"
# → 401
```

四条都对，说明配置完成。

## 5. 三条恢复路径

| 方式 | 依赖 | 什么场景用 | 入口 |
|---|---|---|---|
| **零配置自动恢复** | `VAULT_SECRET` + openid | 换机、重装、清缓存 | 自动，无需操作 |
| **口令解锁** | 你设的口令 | 想让服务端解不开（端到端） | 设置 → 端到端加密 |
| **应急恢复码** | 你保存的 52 位字符 | 前两者都失效（如 `VAULT_SECRET` 被改） | 设置 → 应急恢复码 |

启动时的自动判断逻辑：

```
打开小程序 → 本机有账号？ ──有──▶ 正常显示
                    │
                    无
                    ▼
         云端有数据？ ──无──▶ 空列表
                    │
                    有
                    ▼
     本地有 DEK？─有─▶ 能解开？─能─▶ 自动恢复
             └无            └不能─▶ 提示「需要密钥」→ 跳设置
                    │
                    ▼
        header 是 kdf:'server'？─是─▶ 取 KEK 解包 → 自动恢复
                    │
                    否（口令模式）
                    ▼
              提示输入口令
```

## 6. 版本历史与回滚

- 每次同步**内容有变化**才存档一版，最多保留 20 版
- 入口：设置 → 云端版本历史 → 选一版点「恢复」
- **恢复可逆**：恢复动作本身也会存档，所以当前数据不会因为恢复而消失

接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/vault/history` | 版本列表（时间、大小，不含正文） |
| GET | `/api/vault/history/:id` | 取某版密文 |
| POST | `/api/vault/restore` | 把某版设为当前 |

## 7. 故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 换机进去是空的 | `VAULT_SECRET` 未配或未重新部署 | 跑验证清单第 2 条 |
| 提示「云端有加密数据，需要恢复密钥」 | 本机无 DEK 且 header 是口令类型 | 输入口令，或用恢复码 |
| 提示「云端数据与本机密钥不匹配」 | 本机 DEK 与云端密文不是同一把 | 用恢复码导入正确 DEK |
| 同步失败但无提示 | 自动同步在 `App.onHide`，静默失败 | 去设置点「立即同步」看报错 |
| `503 VAULT_SECRET not configured` | 环境变量没生效 | 检查变量名拼写、是否重新部署 |
| 数据被误同步覆盖 | 本地为空时上传 | 设置 → 云端版本历史 → 恢复上一版 |
| 恢复后仍不对 | 恢复的是错误的版本 | 再恢复另一版；每次恢复都会留档 |

## 8. 与端到端加密的关系

开启「端到端加密」后：

- `header` 变成口令包裹，服务端**再也无法**推导 DEK
- 但同时**失去零配置恢复**——每次换机都要输口令
- `VAULT_SECRET` 处置不当不再导致数据全失（因为已经不用它了）

两种模式的对比：

| | 零配置（默认） | 口令模式 |
|---|---|---|
| 服务端能否解密 | 能 | **不能** |
| 换机输入 | 无 | 口令 |
| 拖库风险 | 防住（缺 `VAULT_SECRET`） | 防住（缺口令） |
| 忘记凭据的后果 | 无法恢复 | 无法恢复（可用恢复码兜底） |
